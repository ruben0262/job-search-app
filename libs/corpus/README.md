# libs/corpus — the shared job corpus and its dedup semantics

Job postings are public, identical for every user, and expensive to acquire. Fit is private,
personal, and cheap to compute. This package is the shared half of that split.

## What the repository does, and what it deliberately does not

**Shared, and the type signature says so.** Nothing in `CorpusRepository` takes a `user_id` — the
corpus holds public postings and no user data may ever land on a row. Per-user reads live in a
separate repository whose methods take `user_id` as a required first argument, so a tenant-scoped
query that forgets its tenant does not construct (`TENANT_SAFETY.md` §1.3).

**One access mode: indexed queries.** The reference exposes two — a materialised `.load()` mirroring
the whole table into memory, and a live `.connect()`. The materialised mode is an artifact of the
JSON store that preceded SQLite, kept only so existing callers survived that migration. Carrying it
to Postgres would mean an O(history) memory pattern in a multi-tenant service. Dropped.

**Two invariants worth knowing:**

- `add()` uses `ON CONFLICT DO NOTHING`, the port of `INSERT OR IGNORE`. **`first_seen_at` is never
  overwritten** — a source re-listing an old posting every cycle would otherwise keep it permanently
  fresh and permanently un-trimmable.
- **A vector can never outlive its text.** Changing a description clears the embedding, and
  `set_embedding()` refuses a vector whose `text_sha256` no longer matches. That is a real race:
  bulk embedding a cold-start batch takes minutes while `refresh.py` runs concurrently, and the
  `(model, dim, version)` assert downstream cannot catch it — the vector space is right, the
  *content* is wrong.

## A schema correction the port surfaced

The first schema draft made `canonical_url` **unique and NOT NULL**. Both were wrong, and the port
is what exposed it:

- The reference keys `all_links` on **`url`** (its primary key); `canonical` and `content_key` are
  *indexed, not unique*. Dedup is a query performed **before** insert, not a constraint. A unique
  canonical looks tighter but turns a case the reference tolerates into a crash mid-harvest.
- Both derived keys must be **nullable**, because `canonical_url()` and `content_key()` return
  `None` for input they cannot use. `NOT NULL` would make such a job impossible to store — silently
  dropping real postings rather than admitting them undeduplicated, which is the wrong direction to
  fail.

Corrected in migration `fe23e709fd46`.

## Why the port was split in two

The dedup **semantics** are pure functions; the SQLite→Postgres move is **storage**. Separating them
means T2 could be written and made green before any storage work started, which is exactly what the
roadmap asks for ("T2 before touching anything") and would not have been possible if the two were
ported together.

## T2 — how the parity proof works

[`tests/test_dedup_parity.py`](../../tests/test_dedup_parity.py), **66 tests**:

1. **Golden cases** — expected values generated by *executing* the reference implementation, not by
   reading its rules and writing down what they appear to say. A misreading transcribed into a test
   would be confirmed by that test forever. Provenance: [`tests/golden/generate_dedup_golden.py`](../../tests/golden/generate_dedup_golden.py).
2. **Behavioural tests** — the same rules restated as intent, so a reader learns *why* from the
   suite rather than from a comment that may have drifted.
3. **Differential fuzz** — 40,000 seeded random inputs through both implementations. **0
   divergences.** Skips where the reference repo is absent, including CI, which is why the goldens
   are committed rather than generated at test time.

⚠ **If a golden fails, the port changed behaviour — fix the port.** Regenerating the golden to make
a red test green is the one move that defeats the entire suite.

## The rules, and why each exists

**Two dedup layers, because one is not enough.** The same job arrives as
`linkedin.com/jobs/view/…` from the LinkedIn scrape and `boards.greenhouse.io/…` from the direct-ATS
poll. URL equality cannot see that.

- `canonical_url` — host lowercased and `www.`-stripped, the two Greenhouse hostnames folded,
  query/fragment/trailing slash dropped. Catches tracking noise and host variants.
- `content_key` — normalised company + title + **location**. Catches the same role reposted across
  boards when no apply URL is resolvable.

**Location is part of the content key, deliberately.** The same title in two cities is two jobs. The
cost is that sources writing a location differently ("London" vs "London, UK") produce different
keys — a missed dedup, which is the safe direction to fail, and the URL layer usually catches it.

**`None` means "no opinion", and callers must fail open.** Both functions return `None` for
unusable input. A caller that treated `None` as a key would collapse every posting with an
unparseable title into one row and silently discard the rest.

## A discrepancy worth knowing about

The reference's own comment claims `"Remote" == "Remote - EMEA" == ""`. **It does not.** `remote` is
stripped from the location but `EMEA` survives, so `"Remote"` yields no location component while
`"Remote - EMEA"` keys as `…|emea`. The behaviour is pinned by a test named after the discrepancy,
because otherwise someone will eventually "fix" the code to match the comment and silently change
what counts as a duplicate.
